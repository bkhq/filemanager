- Dispatch of each wave and every L2 -> `main` merge need explicit user confirmation (no auto mode unless the user asks).
- L1 never pushes; `git push` stays a user decision (the publish workflow deploys only after a push).
- No engine / model pinned: BKD defaults apply.
- Decisions that need the user become BKD messages (contract v2 available).

## Risks

- Parallel edits to `file-manager.tsx` / `router.ts` produce merge conflicts; mitigated by the merge order and L1-side resolution with checks re-run.
- New dependencies (wrangler / miniflare in wave 2, possibly a fuzzy matcher) are risk areas; each plan names them and they need approval with the wave.
- Publishing makes the registry public on GitHub Pages once pushed.

## Scope

Wave 1: 5 tasks in 4 L2 workstreams. Wave 2: 3 tasks in 2 L2 workstreams.

## Alternatives

- Serial L2s (one at a time): no conflicts, roughly 3x wall-clock.
- One L2 per task: more parallelism, more conflicts on the same files.
