## Context

- The trash is a router feature (`server/trash.ts`, 102 lines): with `FmMount.trash`, a delete moves the entry to `/.fm-trash/<id>/<name>` and writes `/.fm-trash/<id>.json` (original path, name, kind, size, deletedAt) through the driver's ordinary `move` / `write`; listing reads those files, restore moves back (`destination()` picks a free name), purge removes both, retention purges lazily on listing or via `purgeExpired(mount)`.
- Router users: `POST /m/:mount/ops` delete (`router.ts` ~1009, returns `trashId` for undo), cross-mount move (source to trash after the copy, ~559), `GET /m/:mount/trash`, `POST /trash/restore`, `POST /trash/purge` (~1255-1370), `hidden()` hiding `/.fm-trash` from listings and search (~364), `FmMountInfo.trash` / `trashRetentionDays`.
- A database-backed driver (bithk `drive_entries`, the planned managed store) already has a trash with its own ids, retention sweep and restore rules. Through the folder scheme it would store `.fm-trash` as ordinary entries, invisible to its own trash and sweep, and its deleted rows would never be marked deleted.
- Client (`client.ts` trash / restore / purge), undo (`react/undo.ts`, restores by `trashId`) and `TrashView` only see the routes; they need no change.

## Proposal

1. **Driver interface** (`server/driver.ts`), optional:
   ```ts
   interface FmDriverTrashItem {
     id: string;
     path: string;        // original path
     name: string;
     kind: FmEntryKind;
     size: number;
     deletedAt: number;   // epoch ms
     expiresAt?: number;  // the driver's own retention, if any
   }
   interface FmDriverTrash {
     /** Moves `path` to the trash; returns the item id. */
     remove(path: string, ctx?: FmChangeContext): Promise<string>;
     /** Newest first. */
     list(): Promise<FmDriverTrashItem[]>;
     /** NOT_FOUND for unknown ids. */
     get(id: string): Promise<FmDriverTrashItem>;
     /** Puts the item back at `to` (the router picks a free path under the original folder). */
     restore(id: string, to: string, ctx?: FmChangeContext): Promise<FmDriverEntry>;
     purge(id: string, ctx?: FmChangeContext): Promise<void>;
   }
   // FmDriver.trash?: FmDriverTrash
   ```
2. **Folder trash as the default implementation**: `server/trash.ts` exports `folderTrash(driver): FmDriverTrash` built from today's functions; behaviour and on-disk layout unchanged.
3. **Router**: one `trashOf(mount) = mount.driver.trash ?? folderTrash(mount.driver)` used by delete, cross-mount move, the three trash routes and `purgeExpired`. `FmMount.trash` still turns the trash on (and sets `retentionDays`); an item's `expiresAt` comes from the driver when it gives one, else from the mount retention. `/.fm-trash` is hidden only for folder trash. Permission checks per item stay as today (read / delete / write on the original path).
4. **Contract**: `runDriverContract` runs trash cases when `driver.trash` exists: delete → listed with path / name / kind, `get`, restore to the original path, restore beside a clash, purge, unknown id → NOT_FOUND.
5. **Reference implementation**: the memory driver gets a native trash (deleted nodes kept in a map), so the router paths for both kinds are tested (memory native, local folder) and the demo's Scratch space uses it.
6. **Docs**: README "Writing a driver" (trash hook), architecture §3, changelog.

## Risks

- Routes and responses keep their shape, so clients, undo and `TrashView` are untouched; trash ids become driver-defined strings (already opaque to the client).
- Memory's Scratch trash changes from folder to native: items trashed before a server restart were already lost (memory), so nothing to migrate.
- A native trash that ignores the mount retention is the driver's choice; the router only purges expired items it lists.

## Scope

`server/driver.ts`, `server/trash.ts`, `server/router.ts` (+ tests), `server/contract.ts`, `drivers/memory.ts` (+ test), README, `docs/architecture.md`, changelog. No client or UI change.

## Verification

- Router tests for both trash kinds: delete returns a `trashId`, list / restore (incl. a name clash) / purge / empty, retention from the driver vs from the mount, cross-mount move trashes the source, `/.fm-trash` stays hidden for folder trash only.
- Contract trash cases pass for memory (native); local, S3, R2 keep passing (folder trash, cases skipped).
- Existing trash e2e (local, folder) and undo unchanged; `bun run check`, full e2e, `registry:smoke`.

## Alternatives

- **Let hosts wrap `remove` to soft-delete**: the router would still write `.fm-trash` and could not list or restore the host's items.
- **Wait for the managed store**: bithk needs this independently of it.

## Annotations

- The memory driver's native trash is opt-in (`memoryDriver({ nativeTrash: true })`) rather than always on, so the router tests built on `memoryDriver()` keep covering folder trash; the demo's Scratch space turns it on.
- `purgeExpiredItems` / `expiresAt` left `server/trash.ts`: retention now lives in the router (`purgeExpiredOf`, `expiryOf`) for both kinds.
